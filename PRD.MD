# PRD — SS_Inventaris: Pesan → Kirim → Terima

## 1. Latar
- Outlet pesan via WA + spreadsheet manual → lambat, human error, tidak terlacak.
- Gudang kirim tanpa bukti terima terstruktur.
- Tujuan: 1 aplikasi web, tanpa login, link unik per outlet/pengiriman.

## 2. User & Role
- Admin Gudang: kelola stock, lihat pesanan, approve/tolak (per pesanan & per item), tandai dikirim / batalkan pengiriman, monitoring terima.
- Outlet: pesan barang + konfirmasi terima via link permanen (wajib login password — link saja tidak cukup).
- Non-goal: PIN/OTP terpisah, expiry token kirim, multi-gudang, harga/faktur, aplikasi kedua untuk outlet. (Login outlet DIKELUARKAN dari non-goal 2026-09-13.)
- 2 link: link permanen outlet `/pesan/<slug>-<token8>` (permanen: form pesan + riwayat + Tab Surat Jalan; token = identitas, password = gerbang — buka link WAJIB login dulu; tutup tab = sesi hilang) dan link berita acara `/terima/<token>` (sekali pakai per pengiriman; tetap link-only tanpa login; fallback/cadangan surat jalan).

## 3. Alur
- P1 Pesan: outlet buka link permanen `/pesan/<slug>-<token>` → Tab `Pesan Baru` (keranjang tanpa angka stock) → submit → `Pesanan/BARU` + info batch masuk & rencana kirim otomatis → popup sukses + otomatis pindah ke Tab `Riwayat`.
- P1b Batas 1 pesanan aktif (Terkunci 2026-09-09): 1 token/outlet hanya boleh punya 1 pesanan aktif (`BARU/DISETUJUI/DISETUJUI SEBAGIAN/SIAP KIRIM/DIKIRIM`). Selama masih ada yang aktif, pesan baru ditolak backend `409` + sebut ID & status aktif (berlaku untuk link outlet MAUPUN Tab Buat manual gudang — blokir total, tanpa pengecualian). Blokir lepas saat pesanan mencapai terminal (`DITERIMA/DITERIMA SEBAGIAN/DITOLAK`). `/kirim` susulan bukan pesanan sehingga tidak terpengaruh aturan ini.
- P1c SOP batal oleh outlet (Terkunci 2026-09-09): outlet TIDAK punya tombol batal; yang mau membatalkan hubungi gudang via WA/telpon → gudang eksekusi Tolak semua item + `Alasan Tolak` (→ `DITOLAK` terminal → blokir lepas → boleh pesan ulang). Tidak ada status BATAL terpisah; `DITOLAK` merangkap fungsi batal.
- P2a Kirim (jalur setuju): gudang approve per item (Penuhi / Tolak per item + keterangan manual) → status `DISETUJUI` (semua dipenuhi) / `DISETUJUI SEBAGIAN` (ada yang ditolak, ada yang dipenuhi) → sistem OTOMATIS membuat record pengiriman berisi item dipenuhi (**stock kurang 1x di titik ini**, atomik dengan approve; TIDAK ada tombol "Buat Pengiriman" manual) → status internal `SIAP KIRIM` (belum terlihat outlet) → gudang klik manual `Tandai Dikirim` (popup konfirmasi "paket sudah diserahkan?") → `DIKIRIM`: link berita acara `/terima/:token` lahir + valid, tombol `Kirim via WA` muncul. Sebelum tombol ini diklik link terima belum valid ("belum dikirim").
- P2a-R Batal kirim (mundur 1 langkah): selama outlet BELUM submit laporan, gudang boleh `Batalkan Pengiriman` (tombol sekundar + popup alasan wajib) → kembali `DISETUJUI`/`DISETUJUI SEBAGIAN` semula, link berita acara lama MATI (dibuka = "dibatalkan, tunggu link baru"), stock tidak diutak-atik, jejak minimal di kolom `RiwayatStatus`. Setelah outlet `DITERIMA`/`DITERIMA SEBAGIAN` → kunci mati, tidak bisa mundur. Tidak ada edit status bebas/dropdown.
- P2c Mirror Pesanan (Terkunci 2026-09-09): baris `Pesanan` mengikuti peristiwa `Pengiriman` (best-effort; sumber kebenaran tetap `Pengiriman`): `Tandai Dikirim` → `DIKIRIM`; `Batalkan` → asal semula (ada TOLAK = `DISETUJUI SEBAGIAN`, else `DISETUJUI`); laporan terima → `DITERIMA`/`DITERIMA SEBAGIAN` (melepas blokir P1b).
- P2b Tolak (jalur terminal): semua item ditolak → `DITOLAK` + keterangan per item (tanpa alasan umum terpisah) → **berhenti, tanpa pengiriman, tanpa kurang stock**. Outlet lihat keterangan per item di Tab Riwayat link permanen, pesan ulang bila masih butuh.
- P3 Terima: outlet ceklis per item sesuai/tidak + jumlah terima + keterangan jika beda + nama penerima → submit → `DITERIMA` / `DITERIMA SEBAGIAN`, halaman terkunci. Gudang read-only (hanya terima info, tidak ada tombol konfirmasi terima).

## 4. Fungsional
- F1: halaman pesan outlet = 3 tab (tanpa BottomNav, di balik login F-login): Tab `Pesan Baru` (default; katalog + search + keranjang, nama + varian + satuan saja TANPA stock, info batch/kirim otomatis, nama pemesan, tombol `Kirim Pesanan`; disembunyikan dan diganti kartu info bila ada pesanan aktif — lihat P1b), Tab `Riwayat` (badge = pesanan aktif belum selesai; filter mungil Aktif/Diterima/Batal/Semua; daftar aktif + riwayat terbaru-di-atas; tombol `Isi/Lihat Surat Jalan` di kartu ber-link lompat ke Tab Surat Jalan) dan Tab `Surat Jalan` (badge = kiriman DIKIRIM perlu lapor; daftar kiriman dari pesanan milik token + form ceklis inline per kartu + arsip terkunci; route `/terima/<token>` tetap hidup sebagai fallback). Validasi stock hanya di sisi gudang saat approve/kirim.
- F-login (Terkunci 2026-09-13): buka link permanen TIDAK langsung masuk — form password inline (username = slug, tanpa BottomNav). Sukses → cookie sesi HttpOnly 24 jam. Sesi = token opaque acak di memori server (BUKAN JWT; restart server = semua logout ulang; password TIDAK berubah). Tutup tab = login ulang (sessionStorage). Password min 4 char, error generik (tak membocorkan slug valid), rate-limit 10/mnt per slug+IP → 429. Password di-set gudang via hub Kelola Link Outlet (ketik 2×, hash scrypt di server, plaintext tak pernah disimpan); password permanen sampai gudang menggantinya (reset-link token tak memengaruhi password). `password_hash` NULL = akses ditolak ("minta password ke gudang"), tanpa jalan pintas link-only. `/terima/<token>` tetap link-only (berita acara sekali pakai).
- F2: buat pesanan manual oleh gudang (masa transisi WA) — T2. Memakai endpoint gudang-internal khusus (kontrak sama, ikut blokir P1b) agar tidak bergantung sesi outlet; Tab Buat untuk token terblokir → 409 juga.
- F2b: `/kirim` Kirim Susulan / Non-Pesanan (T1): pengiriman manual tanpa pesanan (susulan kurang, tukar varian keliru, titipan/promosi); memakai fungsi inti yang sama dengan jalur otomatis approve. BUKAN "buat pengiriman" dari pesanan — tidak ada aksi itu.
- F3: approve per item — Penuhi, atau Tolak + keterangan manual per item (mencakup habis & kurang sebagian). Item ditolak = hangus (pesan ulang manual bila masih butuh, tanpa backorder otomatis). Keputusan dipasangkan by posisi line + cek multiset ID (Terkunci 2026-09-10): ID kembar (`-`, duplikat migrasi) tidak menular — tolak 1 line hanya menolak line itu.
- F4: surat jalan outlet (komponen `TerimaForm` reusable: Tab Surat Jalan di link permanen + halaman fallback `/terima/<token>`): mobile 480px, tanpa nav/BottomNav, bahasa operasional ("Ceklis jika sesuai, betulkan jumlah + tulis keterangan jika tidak"), ceklis per baris item (tanpa ceklis-global; baris bermasalah jangan diceklis + wajib jumlah terima + keterangan), 1 tombol utama `Kirim Laporan Terima` (draf disimpan belakangan = skip), nama penerima wajib, lock setelah submit. Label DITERIMA SEBAGIAN hanya sebagai badge (gudang + riwayat), bukan label form.
- F5: hub gudang `/pesanan` = 1 item BottomNav + 3 tab dalam halaman: Tab `Daftar` (history pemesanan: filter status/slot, aksi Setujui per item/Tolak/Tandai Dikirim/Batalkan Pengiriman — tanpa tombol "Buat Pengiriman"), Tab `Buat` (form pesanan manual masa transisi WA — T2), Tab `Lacak` (Terkunci 2026-09-10: list SEMUA pengiriman langsung terbaru-di-atas tanpa pilih dulu; filter outlet/status/cari menyempitkan; klik kartu expand/collapse detail; batas 20 + `Muat lagi`; tombol Lacak di Daftar lompat ke tab Lacak). Per item Lacak: `Nama | Terkirim: X | Diterima: Y/-` + baris selisih (`N barang hilang/kurang — alasan` / berlebih / keterangan). BottomNav tetap 5 item (Home, Inventory, Pesanan [+ badge BARU di T2], History, Scan ID). List pengiriman + salin/kirim ulang link + reset link per outlet ikut di hub.
- F7: full input manual (Terkunci + dieksekusi 2026-09-10): route `/input` (cari-nama → ketemu = form Masuk/Keluar, baru = form TANPA kolom ID + field Isi per Satuan Gudang opsional, ID auto `MNL-…`), route `/scan` redirect ke `/input`, BottomNav "Input", verifikasi kirim manual ketik-ID per line (`cara: 'manual'`). File scanner tetap di disk, tidak di-route. Backend `POST /api/tambahBarangBaru`: `id` opsional + tolak nama-duplikat 409; gerbang `POST /pengiriman/:id/kirim` tanpa perubahan. Konversi terstruktur (2026-09-10): `satuan_gudang` + `isi_per_gudang` (`1 gu = N satuan`, NULL = terkunci-SO) + metrik kode; parse teks pensiun; `keterangan` kembali catatan murni; dropdown keluar satuan/gudang + preview, tolak merah bila tak ada pasangan.
- F6: notif WA (Fonnte) ke admin gudang saja (`TARGET_NUMBER`; Terkunci 2026-09-09: tanpa nomor outlet + penerima berubah-ubah, maka tidak ada WA otomatis ke outlet): pesanan BARU masuk + laporan terima masuk + link berita acara lahir (untuk diteruskan manual) + pengingat stock yang sudah ada. Link terima ke outlet = share manual gudang (Salin Link + `wa.me` di hub `/pesanan`). WA link lahir berisi path `/terima/<token>` saja (domain publik tak dikenal server; URL penuh via Salin). Outlet memantau status via Tab Riwayat link permanen.

## 5. Data (Supabase + CSV — Terkunci 2026-09-10)
- Gudang di Supabase, diisi via migrasi CSV (`Kertas Kerja Pengadaan F&B - DATA GUDANG PUSAT.csv`); tanpa kolom bulan/tanggal — tiap sel in/out → 1 baris `transaksi` bertanggal (peta: SO 12 Agu 2026; harian 13 Agu–10 Sep 2026).
- `barang_inventory`: `id_barang` (PK, auto `MNL-0001…` urut global 4-digit) | `nama_barang` (`ITEM`) | `varian` | `kategori_bahan` | `satuan` (acuan UNIT SO) | `satuan_gudang` + `isi_per_gudang` (NULL = tanpa pasangan) | `total` (satu-satunya sumber stock) | `divisi` | `keterangan` (catatan murni) | `minimum_stock` | `istilah_data_resep` (alias) | `dibuat_pada`. SO 12 Agu tersimpan sebagai baris saldo-pembuka di `transaksi` (12 Agu 2026 00:00).
- `transaksi`: `id_transaksi` (identity PK) | `id_barang` (FK RESTRICT) | snapshot `nama_barang/varian/kategori_bahan` | `jenis` (Masuk/Keluar) | `jumlah` (numeric) | `satuan` | `harga_satuan` (jejak nilai per satuan; NULL = lama/belum berhHarga) | `dibuat_pada`.
- Data outlet (tetap, pindah ke Supabase 2026-09-10, Sheet dihapus total): tabel `outlet` (`slug` PK = username | `token` UNIQUE | `outlet` | `password_hash` NULL=scrypt, wajib terisi agar bisa masuk) + kontrak `Pesanan`/`Pengiriman` di bawah — halaman pesan mengembalikan baris milik token itu via filter `token_outlet` di layer API, hanya dengan sesi login valid.
- `Pesanan`: ID Pesan, SlugOutlet, TokenOutlet, Outlet, TanggalPesan (`Selasa, 08 September 2026 pukul 08.05 WIB`), BatchMasuk (`Kamis, 10 September 2026`), RencanaKirim, Status (BARU/DISETUJUI/DISETUJUI SEBAGIAN/DITOLAK/SIAP KIRIM/DIKIRIM/DITERIMA/DITERIMA SEBAGIAN), Items JSON [{id, nama, varian, satuan, qtyPesan, keputusan: PENUHI/TOLAK, qtyKirim, keterangan}], Ringkasan, AlasanTolak, RiwayatStatus.
- `Pengiriman`: ID Kirim (KRM-YYYYMMDD-NNN), Token (uuid sekali pakai, lahir saat Tandai Dikirim), ID Pesan ref, Tanggal Buat, Tanggal Kirim, Outlet, Status (SIAP KIRIM/DIKIRIM/DITERIMA/DITERIMA SEBAGIAN), Items JSON [{id, nama, jumlahKirim, jumlahTerima, ceklis, keterangan}], Ringkasan, Nama Penerima, Tanggal Terima, RiwayatStatus.
- Format waktu baku: timestamp = `Hari, DD Bulan YYYY pukul HH.MM WIB`; tanggal slot = `Hari, DD Bulan YYYY` tanpa jam. WIB Asia/Jakarta, konsisten dengan `dateParse` (detik opsional).
- Kolom `Items JSON` = sumber mesin (app `JSON.parse`); kolom `Ringkasan` = terjemahan manusiawi diisi backend otomatis, contoh: `Susu Greenfield 250ml x10 (Penuhi); Gula Pasir 1kg x5 (Tolak: habis)`. Non-teknis baca `Ringkasan`, app baca JSON.

## 6. API
- `GET /api/pesan/:token` (wajib cookie sesi login; slug diabaikan), `POST /api/pesan/:token` (wajib sesi; auto-hitung batch/kirim).
- `POST /api/pesan/:token/masuk` (publik, rate-limit: `{password}` → cookie sesi bila cocok; 401 generik bila salah/belum-set).
- `POST /api/pesanan/gudang` (gudang-internal: buat manual Tab Buat `{tokenOutlet, namaPemesan, items}` — kontrak + blokir P1b sama dengan endpoint outlet).
- `GET /api/pesanan`, `POST /api/pesanan/:id/keputusan` (per item + alasan; guard hanya dari BARU; urutan tulis: validasi stock semua penuhi → fungsi internal `buatPengiriman()` langsung → update Pesanan; saat disetujui otomatis buat record pengiriman + kurang stock 1x, tanpa endpoint buat-manual), `POST /api/outlet/:slug/reset-link`, `POST /api/outlet/:slug/password` (gudang-internal: `{password, konfirmasi}` → scrypt, min 4 char).
- `GET /api/pengiriman`, `POST /api/pengiriman/:id/kirim` (manual SIAP KIRIM→DIKIRIM + generate token terima), `POST /api/pengiriman/:id/batal-kirim` (hanya dari DIKIRIM + belum ada laporan + alasan wajib → kembali semula + matikan token), `GET /api/pengiriman/:token`, `POST /api/pengiriman/:token/konfirmasi` (hanya dari DIKIRIM, tolak submit ganda). - `POST /api/pengiriman` HANYA untuk Kirim Susulan (halaman `/kirim`, tanpa pesanan). Jalur approve pesanan (T2) memakai fungsi internal `buatPengiriman()` langsung, bukan endpoint ini (anti dobel-catat).
- Aturan: validasi stock saat kirim, token outlet 8 char acak permanen (ganti hanya via reset), token kirim 128-bit sekali pakai. Tab `Outlet` (`Slug | Token | Outlet`, tanpa WA/nama orang — identitas orang = ketikan bebas per transaksi). POST pesan dari token berpesanan-aktif → 409 + sebut ID & status (P1b).

## 7. Jadwal Slot (Terkunci)
- Slot: Senin & Kamis, cutoff 15:00 WIB (Asia/Jakarta). Gudang hanya memproses & mengirim di hari slot.
- `batchMasuk` = slot terdekat >= waktu pesan (hari slot tapi >= 15:00 → slot berikutnya; non-slot → slot berikutnya).
- `rencanaKirim` = slot berikutnya setelah `batchMasuk`.
- Contoh: Senin 10:00 → masuk Senin → kirim Kamis; Senin 16:00 → masuk Kamis → kirim Senin depan; Selasa/Rabu → masuk Kamis → kirim Senin depan; Kamis 10:00 → masuk Kamis → kirim Senin depan; Kamis 16:00 / Jumat–Minggu → masuk Senin → kirim Kamis.
- Fungsi murni `hitungSlot(waktuPesan)` + self-check; 1 implementasi dipakai POST & GET.

## 8. UI/UX
- Gudang: BottomNav 5 item (Home, Inventory, Pesanan [+ badge BARU di T2], History, Input [dulu "Scan ID", lihat F7]). Hub `/pesanan` 3 tab (Daftar/Buat/Lacak, aksi Setujui per item/Tolak/Tandai Dikirim/Batalkan Pengiriman — tanpa "Buat Pengiriman"); `/kirim` Kirim Susulan (T1, manual tanpa pesanan); history badge; reuse Bootstrap + BottomNav.
- Outlet link permanen (tanpa BottomNav, 1 link, 3 tab, di balik login): form password saat sesi kosong (username = slug tampil); header outlet + info jadwal; Tab `Pesan Baru` (form tanpa stock); Tab `Riwayat` (filter Aktif/Diterima/Batal/Semua + pagination 5/halaman, daftar terbaru-di-atas, tiket: rel status + langkah-berikutnya + alur + rincian collapse + thumbnail foto); Tab `Surat Jalan` (perlu-lapor di atas + arsip + pagination); Incognito-friendly (tiap tab baru = login ulang). Bahasa operasional di form terima; link berita acara juga dikirim via WA sebagai cadangan.
- Validasi: qty > 0, nama pemesan/penerima wajib, baris terima tanpa ceklis wajib jumlah terima + keterangan, alasan batal-kirim wajib, tolak submit ganda, 1 pesanan aktif per token (pesan baru saat aktif → 409), password min 4 + rate-limit login.

## 9. Definisi DITERIMA SEBAGIAN (Terkunci)
- DITERIMA SEBAGIAN = berita acara mini outlet tentang barang fisik yang masuk vs yang dikirim (sistem menentukan otomatis, bukan dipilih manual).
- Semua item ceklis + jumlah terima = jumlah kirim → DITERIMA. Satu saja beda (kurang/lebih/varian keliru/tidak datang + keterangan) → DITERIMA SEBAGIAN.
- Konsumen: gudang (susulan/retur/komplain, manual per kasus) + arsip (nama penerima + tanggal + rincian per item).

## 10. Non-fungsional
- HP min: HTTPS, kamera AF, Android 9+/iOS 14+, RAM 4GB (fallback 640x480/fps5).
- Scanner tetap: fps10, ideal 1280x720 (tidak diubah).
- Ngrok hanya untuk test; prod perlu URL permanen.

## 11. Acceptance
- [ ] Buka link tanpa sesi → form password (bukan isi); password benar → masuk + sesi 24 jam; salah → 401 generik; 10× salah/mnt → 429; tutup tab → login ulang; outlet tanpa password → "minta password ke gudang".
- [ ] Pesan tercatat BARU + batch/kirim benar untuk 7 contoh jadwal (simulasi jam).
- [ ] Pesan kedua saat masih ada aktif → 409 + sebut ID aktif (berlaku link outlet + Tab Buat); setelah terminal (DITERIMA/SEBAGIAN/DITOLAK) → boleh pesan lagi; token lain tidak terpengaruh.
- [ ] Approve per item + tolak 1 item berketerangan → DISETUJUI SEBAGIAN, record pengiriman TERBENTUK OTOMATIS berisi item dipenuhi + stock kurang 1x (tanpa klik tambahan).
- [ ] Semua item ditolak → DITOLAK + alasan terlihat di link outlet.
- [ ] Tandai dikirim manual → link terima lahir + valid (sebelumnya "belum dikirim"); terima tanpa nama / baris bermasalah tanpa keterangan ditolak; lengkap → kunci + DITERIMA/DITERIMA SEBAGIAN benar; tombol tunggal `Kirim Laporan Terima`.
- [ ] Batalkan pengiriman sebelum konfirmasi outlet → kembali semula + link lama mati + alasan tercatat; setelah DITERIMA/DITERIMA SEBAGIAN → ditolak (kunci mati).
- [ ] Refresh/duplikat submit tidak dobel kurang stock; gudang tidak bisa mengubah status terima.
- [ ] Link tanpa token valid ditolak; reset link mematikan link lama.
